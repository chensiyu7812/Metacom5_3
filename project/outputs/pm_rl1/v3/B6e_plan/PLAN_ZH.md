- 保留回放通过的前缀，按可达终点数从多到少、再按折、再按槽位排序；每折最多 2 个，每个 owner 最多 1 个。

## 预算与显存估计

**显存（只计权重，来自 A0 实测的文件大小）：**

- Gemma-4-12B bf16：22.3 GiB；Qwen3.5-9B bf16：18.0 GiB。
- 两个模型依次加载，从不同时加载。
- KV cache **未实测**：G0 的输入不超过约 3.2k token、批量小，估计只需几 GiB；NeedCard 输入约 15k token，估计也不大。
- 峰值估计约 26–30 GiB，在 A0 规定的"空闲 ≥30 GiB"附近。必须由 A0 实测确认，不能据此宣布可行。

**GPU 时间**，按 A0 的公式：

```text
(输出 token 数 / 实测输出速度 + 预填充与加载时间) / 3600
```

| 项 | 上限 |
|---|---|
| G0 输出 | 128 × 320 = 41k token |
| J1 输出 | 128 × 800 = 102k token（三次全用时为 307k） |
| NeedCard 输出 | 16 × 800 = 13k token |

下面两档**只是假设，不是测量**，用来让研究者判断量级：

| 假设 | 粗略墙钟时间 |
|---|---|
| vLLM 批量推理，总输出约 500 token/s | 约 15–30 分钟（含两次模型加载） |
| HF 单流，约 20 token/s | 约 2–5 小时 |

真实数字以 A0 的实测为准。

## 预检要验证什么（不对自然支持收益作任何主张）

1. 身份：TerminalKey、ExecutionTrace 与回放一致；更换 G、前缀或 bank 都不会复用奖励。
2. 来源：所有阅读内容来自严格过去、同一 owner、family 闭包内。
3. 生成：请求只包含可见前缀和已购买的 ReadingView。
4. 判定：J1 输出能被解析，parse fallback 的比例如实报告，GSC 保持 pending。
5. ER-v1：拒绝计算的原因分布、uncertain 权重、J1 事实和安全失败如实报告。
6. 用 ER-v1 终点表实际运行 BC/PPO 几步，检查表的读取、环境 STOP 查表和缓存回放。
