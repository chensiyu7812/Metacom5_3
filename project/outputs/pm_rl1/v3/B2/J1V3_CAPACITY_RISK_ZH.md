# B2-v3：真实判定前的风险诊断（只做静态检查和 fixture 检查，没有运行 J1）

- 证据等级：engineering_only。
- 原子错误账本 v3 及全部反例测试保持不变、全部通过；没有退回按引文重叠扣分。
- 冻结的判官 v3 身份（`protocols_v3_frozen.json`，`f901812d…`）**没有改动**。
- 结果文件：`j1v3_capacity/CAPACITY.json`。测试：`tests/test_rl1v3_b2_v3_risk.py`（9 项）。

## 1. `{errors, items}` 的最少字段

| 部分 | 字段 | 说明 |
|---|---|---|
| 每个检查项一行 | id、verdict、quote、evidence、errors（5 个都必须出现） | 判 pass 或 uncertain 时，quote 可以为 ""，errors 必须是 [] |
| H− 或 I 判 fail | 还需要 errors ≥ 1 个有效的账本 id | 否则记 uncertain（`fail_without_valid_error`） |
| H+、R、G、S | 只需要上面 5 个字段 | 如果带了 errors，会被忽略并打上标记 |
| 每个原子错误一条 | id、kind、quotes（≥ 1 段回复原文）、evidence | 原文不在回复里、类型未知、证据编号无效，这一条就作废 |

## 2. 最坏情况的规模

- **检查表项数没有硬上限**：NeedCard 不限制条目数。真正的约束来自 writer 自身 800 token 的输出：最便宜的一条（一个失败或被拒绝的建议，配短引文）约 29 token，所以 H 类项最多约 26 项，加上 R、G、I、S 和 5 个风险项，**检查表最多约 40 项**。
- **错误记录数**：最多等于 H−/I 失败项数（每项至少一条）；如果判官把同一个错误拆开写，还会更多。
- **引文长度**：受回复长度约束。G0e 每次最多输出 320 token；最坏情况是整段回复只有一句，并且每一项都引用它。

用 Qwen3.5-9B 原生 tokenizer 计算 J1 输出需要的 token（含结束符；"紧凑"是无空格 JSON，"缩进"是每层缩进 1 格的 JSON）：

| 检查表 | 回复 | 只给判定 | 每项引一句 | H−/I 全部失败 | 最坏 |
|---|---|---|---|---|---|
| 最小（8 项，无历史） | 一般（114 token） | 167 / 368 | 319 / 520 | 475 / **810** | 551 / **898** |
| fixture（13 项） | 一般 | 270 / 591 | 537 / **858** | **819** / **1,376** | **952** / **1,530** |
| fixture | 长（248 token） | 270 / 591 | 694 / **1,015** | **1,060** / **1,617** | **1,276** / **1,854** |
| 中等（17 项） | 长 | 351 / 768 | **912** / **1,329** | **1,334** / **2,021** | **1,580** / **2,291** |
| writer 上限（40 项） | 长 | **850** / **1,819** | **2,203** / **3,172** | **3,857** / **5,844** | **4,781** / **6,858** |

每格前后两个数分别对应紧凑格式和缩进格式；加粗表示超过 800。

**结论**：原定 `J1 max_new_tokens = 800` **明显不够**。
- 13 项的 fixture 检查表，判官只要按提示词给每一项都引一句（并且用缩进 JSON），就已经超过 800；
- 40 项时，即使只给判定，也超过 800。

**这是尚未实测的容量风险**：真实判官输出多长、用不用缩进，都还没有数据。

## 3. 截断以后会发生什么（拒绝路径，fixture 已验证）

| 情况 | 结果 |
|---|---|
| 输出被截断成半截 JSON | 解析失败，原样重问；贪心解码下会再次被截断，于是**所有项**都记 uncertain（`parse_failed`）。ER-v3 拒绝计算（`too_uncertain` 和 `hard_safety_uncertain`），终点保持 pending，不会猜测结论，也不会记 0 |
| 有项目缺失 | 只针对缺的项重问；仍然缺的记 uncertain（`missing_after_retry`）。如果缺的是安全项，ER 拒绝计算 |
| 证据编号错误 | 在行里会被丢弃并打标记（`bad_evidence_ref`）；在账本里，这条错误作废，引用它的 fail 改记 uncertain |
| 原子错误冲突 | 引文重叠记 uncertain（`overlap_ambiguous`）；行与账本矛盾记 uncertain（`ledger_row_conflict`）；没有有效错误就判 fail 也记 uncertain。这些都计入不确定权重，超过 1/3 时拒绝计算 |
| ER 与 GSC 的隔离 | ER-v3 记录里没有任何 GSC 字段，`is_gsc=False`；只有 J1 时 GSC 为 pending（None, None）；终点登记只接受 ER-v3 |

所以截断不会产生错误的分数，但会导致**系统性的 pending 和拒绝**。规模一大，B6e 可能几乎没有能计算的终点。

## 4. 新版本方案（只是提议，未采用；研究者批准后才在首次 J1 调用前固定）

判官协议 v3 的文字和账本规则都不改。J1 的解码配置原本就要在首次调用前写入 `JudgeIdentityV3.id`（decode_id），这里提出它的版本：

**J1 解码 v1 提议（`j1-decode-v1`）**
1. **按前缀定额**：检查表冻结后，用本诊断同样的方法算出该检查表在"长回复、全部失败、缩进 JSON"下需要的 token 数，乘以 1.25 再向上取整到 256 的倍数，作为该前缀的 `max_new_tokens`；上限 4,096。算出来超过 4,096 的前缀在调用前就标为阻塞，不调用、不截断。
2. **记录结束原因**：每次 J1 调用记录 finish_reason。因长度结束的标为 `truncated`，与格式错误分开统计；不再原样重问（贪心解码下重问没有意义），直接按解析失败处理并保持 pending。
3. 预计开销：13–17 项的检查表，每次调用约 1,500–2,600 token 的上限。B6e 的 J1 上限按此重算时间，**调用次数上限不变**（≤ 360）。

备选：判官协议 v4，要求紧凑 JSON、pass 行不写 quote。这样能减少约一半 token，但会改变提示词和判官身份，需要另外冻结，所以不优先推荐。

无论选哪一种，都需要研究者批准，并在第一次 J1 调用之前冻结。
