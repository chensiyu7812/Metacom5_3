## 3. B 的审核发现（批准前需要知道）

1. **按现在的数据，U3−U2 这个主要比较基本测不出东西。** 排序项只作用于 2 行（0.9%）。30 步里最多 2 个累积组的梯度与 U2 不同，而且系数只有 0.1，会再被组内平均进一步稀释。所以 U3 和 U2 实际上几乎是同一次训练；结果不显著也不能说明“回复级排序监督无效”。原因是只保留逐条核查且证据实际送达的非首选回复。review50 中 11/50 题有可辩护排序候选，并非“全部官方负例只有 22% 正确”；其中 5 题属于 development、3 个 fit 候选证据未完整送达，只余 2 fit / 1 tune。不能把 development 或缺失证据的候选直接放入训练。
2. **训练规模很小。** 只有 30 个 optimizer step、LoRA r8、lr 1e-4。冻结主要比较仍是 U3−U2，不能事后改成 U2−U0；后者只是原定次要的回复 SFT 迁移探索。另有监督内容限制：fit 中 204 条弱监督建议、27 条当前请求支持的通用回复，只有 3 条保留为送达历史支持的个性化候选。
3. **训练提示与 MCQ 评测提示的版式不同。**
   - 实际 joint_release 训练用 B `behavior.build(U0, recall_suffix=False)`：与 MCQ 相同的情境系统提示和合法原始证据，不带回忆后缀、选项和短答案格式要求；旧 `reply_protocol` 通用系统提示版本仅是过渡资产；
   - W4-0 / W4-E 的 MCQ 沿用已冻结的 WP3 版式：情境系统提示 + 回忆后缀 + 选项指令；
   - 普通离线开放回复可以使用训练版式；完整 Agent 还会加入当前短上下文、实际需求选择和适用技能，因此需在实际 episode manifest 中核对，不能先验宣称整条系统输入完全相同。
   因此 MCQ 上的迁移效果会被这一差异削弱。这是有意保留的（MCQ 协议已冻结），报告时会写明。
4. **8.4k token 的反向传播耗时和显存都没有实测。** 每种方法 1,494 s 的上界是按 4 倍前向估算的。前 20 步烟测（占 30 步的三分之二）会实测；如果预测会超出上限，就停止并报告。
5. **研究者要求的 NoMem/OptOnly 训练后诊断，原 A 资源候选未包含。** 原话是“检查训练是否利用历史，而非仅学习选项风格”，只能在训练后的模型上回答。B 将其列为单独候选块（§5 W4-E-diag）；A 已提供 `manifest-adapted --diagnostics-only` 和适配身份 scorer，单独生成 1,088 请求且不重复主块。默认主 manifest 仍为 544 请求，诊断块需明确包含在研究者批准中。

## 4. 两个可选方案（一次批准即可，不再拆轮）

- **方案 1：按现有数据执行。** U3−U2 保留原主要比较身份并声明信息不足（只有 2 行带排序信号）；U2−U0 仅作预定次要探索。A 不推荐直接用此方案检验记忆理解/排序监督有效性。
- **方案 2（B 推荐）：训练前先由 A 补充经核查的非首选回复。** 这一步不用 GPU，优先补足真实历史依赖的正例支持和经核查的相对负例。30% 仅是 B 的覆盖示例，不能成为强造负例的硬配额；不根据开发题答错情况选训练样本。补完后用同一个 `check-reply` 重新核算。批准条件写成“实测上界 ≤ 下表方案 2 的上限”，其余条件不变，所以不需要第二轮审批。如果实际支持不足，应报告剩余缺口；只有研究者明确接受信息不足的探索目的时才执行方案 1，不自动把比例不足改成负例标签或更换主指标。
