## 2. 四头如何组织，以及哪些问题现在确实能改善

`resource_evidence_views.py::EvidenceViews` 复用已存在的 `TemporalEvidenceLedger`，重新验证导出、每轮原文身份、同owner和严格过去条件，以及候选证据依赖。没有另造身份体系。

- **MP**：保留已有 target-time slot 视图；报告序列指向原文跨度，不把最新报告自动宣布为当前事实。完整旧更新链仍未重新编译，当前输出不是“已修复所有MP更新”。
- **ME**：保留已有阶段/事件时间/结果字段，未知仍未知。图中目前可确定的是“共享这段原文”，不能由此自动生成 `outcome_of` 或把意向改成完成。
- **MS**：新增显式呈现版本 `pmrl1-source-views-v2-20261030`。字段名只定义一次，随后列出全部 `[轮次、说话者、原文]`。检索词项匹配移到审计回执，不反复塞进 G。原始全文仍永久保留，未加人工 token cap。
- **RS**：现有来源隔离和 canonical atomic 接线继续有效。现阶段能够比较定位变化；需要新语义依据的适用条件仍列为缺口，不从策略家族或实施者意见生成 reward/fit 标签。

v1 的逐轮重复字段及匹配元数据使6组呈现多出775–1,015 tokens。v2 保留完全相同的轮次内容，精简序列格式，增量降为57–65 tokens。这是可复算的布局开销降低，不是语义能力提高。v1/v2 均保留，固定前缀选择不变。

这些变化让主体、来源和轮次更容易定位，但 **“能定位原文”仍不是“能判断原文支持该断言”**。例如，原文“我打算申请”可以准确定位，却不能据此认定“我已申请成功”。后者需要明确阶段核查与反馈证据；不会靠多加一层目录自动解决。

## 4. 本轮找到并修复的真实 J1 接口问题

旧准备清单指定 `feedback_prototype.repair_payload`，但该函数仍校验旧 `evidence` 审查格式，并以回复缺陷作为触发条件。新版审查已经使用 `source_evidence` 和 `score_review`；直接接入会校验失败，也不能正确处理仅有评分依据问题的情况。

新 `development_feedback.py::DevelopmentAdapter`：

1. S 保留原完整量表和已准备的完整 schema 请求，22项真实 wire 重建一致。
2. A 复用现有 score-aware audit 和 Beta strict 交付代码，实际请求包含完整原始证据、回复、量表、分数身份和工具schema。strict过去失败仍是失败，没有因此宣称可靠。
3. R 按当前审查格式校验来源和分数链接，以现有 `feedback_score_audit.decision` 为触发依据。即使没有回复缺陷，只要质量/严重度/覆盖依据需要补核，也能进入一次补核；已计入的回复缺陷不自动再采样。
4. R 带原q/m量表、完整源、原分数、当前审查及完整最终schema。没有改量表、平均、补零或“直到满意为止”的重复。

`OfflineDevelopmentStage` 复用 `RecoverySchedule`，按 S→A→R 三个依赖波次持久化。每条最多2次技术恢复，三波次共享16次；相同配置连续3次同类技术失败触发既有熔断。未触发的R不调用；初评不可用则记录依赖缺口；schema有效的语义unknown可以接受审查，但保留空q/m，不变成0。首份有效结果绑定下游，所有失败保留。送达/结果未知不重发。

**明确剩余边界**：这次交付的是完整开发阶段的离线调度与可复用请求适配，不是生产派发已完成。类名和实现均明确 `OfflineDevelopmentStage`，拒绝非合成transport。尚需把真实transport、实际用量、累计调用身份、共享预算原子预留/结算及阶段授权接到该调度规则；不能将合成零费用回执交给真实流程。正式训练继续由现有 `QualifiedFeedbackBackend` 检查资格，开发阶段不要求先合格，二者不得混用。
