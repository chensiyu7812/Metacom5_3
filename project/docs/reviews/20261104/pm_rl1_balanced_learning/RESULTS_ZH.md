# 按情境选择质量与等待的平衡点：本轮实现和真实复测

2026-11-04。接续 `edffc7c`，响应研究者“综合考虑，针对不同情况，尽量找到收益最大化的平衡点”。本轮完成了保持资源和回复不变的在线优化，以及 BC、OneShot、PPO 的共同质量—秒数目标适配；真实自然支持学习仍未开始。

## 1. 已取得的实际收益

在原冻结 G/P2 与 BGE-M3 上，对已有两个 train 情境按同一动作程序 `6×GET_MS → STOP`，交错比较原实现与请求内精确缓存。每情境、每实现各3次，另2次预热，共14次新 G，全部自然结束。G/BGE各加载一次，实际98批单块BGE编码、98次未训练PM前向；动作仍为脚本重放。

| 情境 | 原实现完整等待中位数 | 优化版完整等待中位数 | 逐重复配对差的中位数 | 配对首段等待变化 |
|---|---:|---:|---:|---:|
| C02 | 5.303秒 | 4.962秒 | −0.337秒 | −0.336秒 |
| C03 | 8.015秒 | 7.751秒 | −0.306秒 | −0.304秒 |

配对差中位数与两列中位数相减不是同一统计量，尤其C03不能混用。12条正式测量及2条预热的原始回复和token序列全部与历史结果一致，因此C02既有人评继续有效，无需重答。本轮未调用评分API，新增费用0。

优化来自 `RequestRenderer` 对完整输入/资源集合的请求内缓存，以及STOP时复用没有变化的内部观察。每个请求都重新建立缓存；未使用跨请求历史生成结果替代本次G。全量487个既有程序重放通过，591个已编码公共观察完全相同，实际usage计算由13,504次降为6,928次（减少48.7%）；完整动作顺序、可用性、实际资源、终点请求都保持。FullText和NoText语义均有回归检查。

这里计量的是模型常驻、单并发、参考客户端同一时钟的发送→首段/完整文本，含实际在线读取、BGE与PM计算；不代表网络浏览器部署、冷启动或生产p95。两个情境、三次重复只能支持本次路径比较。优化版G阶段中位数仍约4.16/6.90秒，减少重复检索计算没有消除生成本身的等待。

首次准入在加载前被原GPU守卫拒绝：最后XML利用率2%，空闲48,551MiB，可见进程为空；未据此猜测另一个作业，也未加载或调用G。继续CPU工作后仅再检查一次，最后XML利用率0%，按原标准进入原14次范围。两次检查、首次失败日志及加载记录均保留，未更换设备、终止其他进程或放宽守卫。

## 2. “综合考虑”如何进入训练

新的显式目标为 `R = Δ(q/4 − m) − λ × 客户端完整等待秒数`。质量、误用和等待仍分别保存，TTFT单独报告。tokens保留为资源诊断/公共输入，不再在这个目标上扣第二次费用。旧TokenCost路径保留历史身份，新实现通过 `balanced_objective.py` / `balanced_learning.py` 显式启用，旧脚本不会自动变成新训练。

λ须明确给定，并在同一比较中一致使用。给定同一λ，不同情境的质量增益、资源相关性及后续等待不同，因此最优资源/数量/STOP也可以不同；不需要为每个案例事后调λ。读后状态的回报只计算从该决策起的后续等待，已经花掉的时间不会再次成为继续读取的理由。第一个转移计入初始化开销，全部分段之和精确等于完整客户端等待。

BC按这个回报重选完整程序及逐步动作，价值初始化使用各状态的剩余回报；OneShot回归每个实际测过的程序；PPO替换全部旧奖励字段后调用原优化器。三者共享质量定义和λ，但时间必须来自各自真实执行路径：固定读取的OFF耗时不能充当顺序策略STOP，固定MS6不能充当OneShot规划，FullText、NoText及不同实现的时间不能混填。

每份时间证据绑定实际输入、资源、回复、部署条件、实现路径和可见性；PPO进一步要求计时记录对应当前行为参数。两轮脚本重放的时间均没有这个行为绑定，不能被协调器当成自然PPO反馈。协调器已支持缺失时间等待、16条完整反馈后更新、时间证据随检查点保存、更新中断恢复，以及64/128轨迹处同目标开发集检查。

35项相关测试通过，其中包括原BC/价值初始化、OneShot优化器、实际PPO更新后再采样、128条合成轨迹及开发集、收集中断和更新中断后的精确恢复。这些验证使用明确合成质量/时间；没有成为自然研究结果。测试中的λ取值仅为工程用例，未选择部署权重。

## 3. 真实奖励目前还差什么

独立复核两轮共40条真实轨迹，其中36条非预热时间记录可以精确绑定现有菜单和回复。旧轮覆盖6个固定终点和2个顺序终点；新轮每种实现各覆盖同2个顺序终点。重复测量不增加独立情境数。实际顺序STOP、OneShot规划、NoText时间记录仍各为0；完整菜单仍有487个终点，不能由这几个终点代表全部。

真实质量交接仍为 `PENDING_QUALITY`，合格训练目标、自然BC检查点、自然PPO更新均为0。编译器对缺失质量、缺失计划内时间均不发布部分训练表，不把未测当零，不悄悄缩小菜单。当前任意新策略的实际执行计时服务及其冻结绑定也尚未交付；本轮交付的是经过优化器/恢复验证的接收端和有限真实路径证据。

这仍不能推断RL学不出来。当前证据支持的是：执行开销可减少；不同终点的质量增益仍缺少足够可靠、绑定准确的覆盖。仅在这两个固定程序上节省约0.3秒，不能证明读资源整体值得，也不能证明顺序适应优于OneShot。

## 4. 研究接续的具体取舍

先保留共同的质量—延迟前沿，避免把某一个λ的结果当作唯一能力结论。达到相近质量时，优先较短等待；增加等待时，要看到可辨认的质量/误用改善。不能通过追求更多GET、更多token或只追求更快来定义成功。以固定质量可接受范围/延迟偏好的敏感性比较确定权衡后，再统一用于所有方法，不按测试结果挑权重。

质量侧继续复用已有35条参照及澄清。C02“个人感觉相当，B90/A95、很接近”是小增益/不确定性的参照，不转成q/m、不取区间中点、不硬填平局；当前同文本的新计时可与这条判断共同分析，不能替用户把几秒等待换算为确定效用。旧8对不自动重发，也不把全部487终点要求为人评任务。

下一步优先使用已定位的真实读后STOP/追加读取对照，检查高增益、近等价和误用三类中，哪一项未决判断会改变动作。质量判定流程能复现这些已有参照后，才适合扩展到实际训练回复；必要新人评只补有决策价值的缺口，并保留区间/无法区分。原收费额度仍保留，但本轮没有恢复付费派发或要求充值。

时间侧应先补顺序STOP及OneShot实际规划路径，再将当前参数的采样/重放接入计时，按方法分别冻结来源。完成这两个输入后，现有适配器可使用真实BC初始化和16条完整轨迹启动原PPO。当前优先级是获得可比较的真实训练信号，而不是继续优化毫秒级MLP或扩大重复题目。

原453份冻结文件和原费用账本均验证不变。原付费阶段19次尝试/18份S/1未知、A=0的状态不因本轮工程完成而改变。
