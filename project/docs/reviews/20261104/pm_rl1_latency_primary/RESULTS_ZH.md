# PM-RL1：用户等待延迟为主目标，tokens为研究代理

2026-11-04。研究者明确：“真正很影响收益的，是实际部署时的延迟……tokens的消耗，实际部署时，用户并不在乎，仅仅供研究用。延迟才是我们的目标。”本文件记录该明确修正，机器可读定义见[OBJECTIVE.json](OBJECTIVE.json)。

**当前研究目标是：在保持当前回复质量、控制误用的条件下，改善用户实际等待时间。tokens仅为研究诊断、容量约束和可能的延迟预测特征。** 不再用“省tokens”直接代表部署收益，也不另加用户没有要求的token效用惩罚来重复计成本。

## 与旧方案的关系

9月28日原实施方案第9节明确选择先用资源tokens训练，把真实延迟作为报告和后续扩展。当前`TokenCost`及学习协调器确实仍执行这个代理目标。

研究者本次指示覆盖“延迟仅作后续扩展”的方向选择；后续主实验应对齐延迟。旧token配置、产物和原方案作为历史保留，不回写为已经优化过延迟。已有token实验若继续用于工程诊断或代理基线，必须明确命名，不能充当新主目标下的学习结果。

上一轮对C02的0.11885成本、2,048 tokens假设盈亏平衡点，以及全池U分档大于token成本的推导，**只描述旧token代理目标**。它们不能判断A在真实部署中是否值得，也没有把研究者的90/95类比换算成毫秒或美元。人的质量判断继续有效，部署取舍需要真实延迟依据。

## 用户路径怎样计时

在同一个客户端单调时钟记录：发送请求（任何方法的PM/检索尚未开始）、看到/收到第一个非空实际回复文本、看到/收到完整自然结束回复。

- 首段等待TTFT：发送到第一个实际回复文本；空事件、心跳、“正在处理”占位不算。
- 完成等待：发送到完整回复。延迟主汇总沿用既有项目测量思路，报告p95完成等待，并同时报告p95首段等待、p50和失败率。
- 有浏览器事件才称浏览器可见延迟；参考客户端测量就明确称参考客户端端到端，不冒充生产UI体验。非流式客户端的首段可见时间可能等于完成时间，不能据此虚构模型首token时间。

在线PM初始编码、所有决策、OneShot计划搜索、每次检索/编码、组装输入、G预填充与完整解码、排队和客户端交付都属于各方法的真实路径。OFF只计它正常运行所需的工作，不能为了公平强行给OFF加入本不需要的PM开销。

训练裁判、人评、离线训练及预建静态索引不在用户响应路径。常驻模型的热态与冷启动分开报告；若请求实际触发加载，冷启动路径就应包含它。输出长度影响真实等待，不能靠强行截短回复取得虚假低延迟。

## 已有数据能支持什么

本轮实际审计431条真实生成导出，核对原包、反馈来源及814份raw/seal文件。

| 可用记录 | 数量 | 可作何用途 |
|---|---:|---|
| G组件`generation_seconds` | 431 | 组件诊断，含407条新生成与24条历史OFF复用 |
| 客户端首段等待 | 0 | 尚不能估计用户TTFT |
| 客户端完整等待 | 0 | 尚不能估计用户完成等待 |
| PM→检索/编码→G→客户端完整轨迹 | 0 | 尚不能判断策略的部署延迟收益 |

代码中的G计时在chat tokenization和输入搬到设备之后才开始，在生成、同步及解码后结束。它不含完整PM、检索、特征编码、网络或用户界面，也不记录首段可见事件。此前整批BGE耗时也不能平均摊到每个请求，冒充实际逐次读取的在线成本。

C02 A的历史G组件记录约4.152秒，B约2.121秒；A是新批次生成，B来自历史OFF。这两个数保留作诊断，**不报告为A让用户多等了2.031秒**：它们没有同条件交错重复、完整在线路径或客户端计时。真实端到端差值保持缺失。

更多tokens是否更慢、慢多少，要在选定部署条件下测量；读取轮次、缓存、编码、输入准备、输出长度和负载都可能改变关系。不能把旧`0.05/2048`系数重命名为“延迟成本”。

## 训练和评价怎样接上目标

先补齐同一条部署路径的客户端计时，用同一模型/解码/硬件、声明的缓存与并发策略，交错重复比较OFF、固定计划、OneShot及顺序策略。训练终局缓存复用不是一次新的部署请求；真实部署可用的缓存要按同一规则给各方法，并区分命中、未命中与训练回放。

保留所有失败与超时及其实际已等待时间。未完成的潜在完成时间有删失，不能伪称已经完成，也不能从可靠性结果中删除。旧Paper-1汇总代码有60秒处理及旧任务/arm类型，不能直接套用并自动给RL1增加研究者未指定的时限。

以质量—延迟关系判断收益：在可接受支持质量和误用风险下，看用户等待是否改善。轻微质量差是否值得额外几十毫秒或几秒，要放回这两个实测尺度；研究者未指定具体秒数边界时，先报告可比较方案与敏感性，不自行设一个论文通过门槛。

训练代价需要实测延迟或在同部署条件下验证过的预测器。一个候选总回报为`质量/误用效用增量 − λ_L × 端到端秒数`，λ_L尚未选定；同条件OFF延迟作为基线相减只改变相应常数，不需要部署时再生成OFF。总延迟只扣一次，不能保留原GET token扣费后再叠加完整时间，把同一种效率成本重复计算。若按阶段分配耗时，必须与总路径精确一致。

每次请求的平均时间惩罚不自动等于优化p95；训练平均收益、尾部等待和质量约束需要分别验证。预测器不能读取未取得的资源或未来真实回复长度作为在线策略输入；未来信息只能作为离线拟合目标，不能泄漏给actor/critic。缺失延迟仍是pending，不填0。

**本轮完成的是目标修订和现有测量覆盖审计。** 没有假装已修改好延迟奖励、完成部署测量或启动真实RL。下一项必要工程工作是完整用户路径的计时与有界配对测量，再据此接入训练代价；这些本地计量不需要恢复付费裁判。
