# V5.3全组件状态总报告：V5.2到现在，修了什么、提升了多少、还剩什么（2026-08-06）

本报告回答一个问题："5.3能不能确保没问题，学出来的PM能用，和baseline可比，结果有意义？"
覆盖MP/ME/MS/RS四个组件 + Step1（训练管线）+ Step2（真实生成兼容门），按"V5.2是什么状态→
V5.3现在验证到什么程度→还剩什么没修"的顺序整理。取代之前的`PM_V1_5_V5_3_CONSOLIDATED_
FINDINGS_20260806_ZH.md`（那份文档写于ME/MP/MS真实效果测试和Step1试点之前，现在信息已经
过时，具体分项证据仍保留在各自的分项文档里，这里只做最新的汇总判断）。

## V5.2的根本问题：不是某个组件的bug，是生成器根本看不到证据原文

`compose_locked_response()`是确定性字符串拼接——LLM从来没有真正看到MS/ME的证据文本，只是
把模板片段拼在一起。这意味着V5.2时代做的任何"MP/MS/ME候选质量"评估，都测不出"生成器会不会
正确使用这个证据"这个问题，因为生成器根本不参与证据使用这一步。V5.3的typed response program
（生成器看到完整typed证据，产出一次整合过的回复，配一层guard+rewrite+兜底的安全网）是专门
针对这个根本问题设计的，本报告里几乎所有"V5.3新发现的bug"，都是这个新架构第一次让"生成器
怎么用证据"这件事变得可测试、可观察之后才发现的——V5.2不是没有这些问题，是V5.2的架构让这些
问题不可见。

## 二、ME（情景/可复用经验记忆）——反推数据后找到根因并修复，从"无效"变成"可用"

**2026-08-06后续更新**：用户明确要求"通过EvoEmo/ESConv/ES-MemEval的真实数据和V5.2的历史
经验反推ME这个老问题的真实根因"，而不是继续沿用"保守关闭"的结论。真实动手核查后，结论整体
改写：

| | 状态 |
|---|---|
| V5.2 | 同上，不可测；V5.2自己的历史根因文档（2026-08-02/03）其实已经诊断出"EvoEmo compiler把任意过去episode都叫ME，跟内部'可复用结果'定义不共享可用性定义"，但当时没有真正动手修 |
| 三个数据源反推 | ESConv没有跨会话用户ID，结构上不支持ME（不是ME的问题）；ES-MemEval官方418道QA题（V5.2时期独立审计）也是0个可执行ME候选，原因文档原话"ME不是benchmark没有事件...V5.2的ME合同更窄"——跟这次独立发现的0/138是同一根因在不同数据切片上的重复验证；EvoEmo真实随机抽样40条，约15-20%真的符合"试过+有观察到结果"这个窄定义，"事件"本身确实最多（62.5%），但多数是未解决/背景性的，不是可复用结果 |
| 严格编译器 | 原0.40%（3/1215，18用户全池口径）——逐条人工核对新分类出的候选，找到并修复三个具体正则漏洞（动词表太窄、只认"I/we"主语、只认过去式结果），同时新增3处假阳性防护（目的从句、假设语气、帮别人被误判成自助）。**修复后：23/1215（1.89%，7.7倍提升），人工核对约21-22/23站得住，精确率没有下降**，6个原测试全过+9个新测试全过，无回归 |
| 排序层断链 | 更深一层：排序函数`typed_tier`早就设计了"优先选ME_REUSABLE_OUTCOME类型候选"的机制，但从来没有调用方真正计算并传入`me_subtype_hint`，导致机制形同虚设。新写`me_subtype_hints()`把编译器结果接进去，**真实138个state的命中率从0变成108/138（78%）**，抽样人工核对8个新命中的候选，跟当前对话主题基本贴合，没有文不对题的注入 |
| Step1最小试点重跑 | 9个真实state（新的真实上限），**9/9拿到有效judge判定：2胜2负5平**，带ME一侧8/9生成clean（高质量信号），不带ME一侧的残留兜底是已知的M0+R0问题，不是ME特有的新问题 |

**判断：ME不再是"安全但无效"，是真实可用的组件——根因是两处具体、已修复、已验证的工程缺口
（编译器覆盖窄、排序层断链），不是数据不支持。可以进入V5.3。**

## 五、Step1（训练管线）

- 此前判断：全量训练成本高（每组件几十到几百次真实调用），未经管线验证前不该直接投入，
  提议先做"最小试点"（单组件、10-20个真实state、带/不带对照、真实judge打分）验证管线本身
  能不能跑通。用户批准后先做了MP，这次扩展到MS/RS（ME最初因0命中无法测，反推修复根因后
  补跑，见下）。
- **管线本身：验证通过**——四个组件（MP/MS/RS/ME）全部真实跑通了"生成→真实judge打分
  （复用已有的正式judge instrument，正反序配对+4项风险判定）→提取信号"全链路，累计上百次
  真实API调用（生成器+judge两侧）。过程中发现并修复2个试点脚本本身的bug（judge遇到瞬时
  provider错误会崩掉整批；格式修复重试没有真正生效），随后在MS/RS/ME试点复用时未再复发。
- **管线之外，发现了2个真实的核心代码bug**（不是试点脚本的bug，是`v1_5_v5_3_typed_
  response_program.py`本身的bug）：M0+R0证据幻觉（见MS一节）、RS guard契约不适配（见RS
  一节）——这两个修复的价值已经超出Step1试点本身，直接影响V5.3生产路径的正确性。
- **仍未做的**：正式的、使用"已认证裁决模型"（需要预先跑qualification report）的全量Step1
  训练。这次做的是"最小试点"这一档，不是完整训练——这是此前明确商定的范围，不是遗漏。

## 六、Step2（真实生成兼容门）

此前（本次扩展之前）已经做过约58+次真实调用，修复验证了说话人归属、记号回显、化名指代三个
bug，判断"基本solid"。这次扩展通过Step1试点，**真实触碰到了此前Step2测试从未覆盖过的两条
路径**（真正的M0+R0、真正的RS）——覆盖面变宽后，又发现了2个新的真实bug（M0+R0证据幻觉、
RS guard不适配）。这说明"基本solid"这个判断本身是对的，但覆盖面此前不够全，现在更全了，
也确实多找出了问题——这是覆盖面扩大的正常结果，不代表之前的验证是错的。

## 七、所有组件共同的一个已知缺口：judge没有别名映射——**已修复**

Step1的MS试点里发现：EvoEmo的证据文本习惯用第三人称叙事（比如把用户叫"Anna"），生成器
拿到了`current_user_known_aliases`能正确把"Anna"解析回"you"，但risk judge没有拿到同样的
映射，会把这种**正确的**指代解析误判成`unsupported_personal_claim`违规。这个问题在MP/MS
试点里都出现过。用户明确要求一并修正后，给`v1_5_mvp_judge.py`的两个message builder加了
一个纯新增、默认关闭的`current_user_known_aliases`参数（不传=跟修复前完全一样的prompt，
已认证的正式Step1 judge管线不受影响），并接进了MP/MS/RS/ME全部四个Step1试点脚本。9个
既有测试全过（未改变默认行为），加了2个新测试验证新参数行为。

## 八、总体判断

按用户设定的门槛（"能用、和baseline可比、结果有意义"，不是"发表级完美"）：

- **MP、MS、RS、ME：全部四个组件都可以进入V5.3。** 已知的correctness bug都已修复并用
  真实数据重新验证过，质量效果MP中性、MS明确正面、RS方向正面（样本较小）、ME中性偏正面
  （样本较小，跟MP相似）。ME是这次反推工作里状态改变最大的一项——从"完全打不出候选、
  安全但无效"变成"78%真实命中率、真实配对测试2胜2负5平、带ME一侧89%生成clean"，根因是
  两处具体、已定位、已修复的工程缺口（编译器覆盖窄、排序层的`me_subtype_hint`断链），
  不是数据不支持——这是直接翻真实数据（EvoEmo/ESConv/ES-MemEval）+ V5.2历史文档反推出来的，
  不是重新猜测。
- **Step1：管线验证通过，全量训练未开始。** 四个组件的真实generate→judge→信号链路现在
  都跑通了，但"用已认证裁决模型做的正式训练"这一档还没开始——这是此前商定的范围边界，
  不是遗漏。
- **Step2：更全面地验证过，新发现的问题已修复。**
- **judge别名映射缺失：已修复**（opt-in、向后兼容，已接入全部四个Step1试点脚本）。
- **仍未修的已知项**：M0+R0证据幻觉修复后仍有约30-33%残留（明显改善，未完全消除，是
  概率性的模型行为，不是逻辑漏洞）；ME排序层目前对"非REUSABLE_OUTCOME"候选一律给0分，
  没有区分UNRESOLVED_EVENT和CONTEXT_EVENT（真实分类数据显示两者占比不同，但目前没有
  可靠的机械分类器区分，暂时不影响结果，因为只要有REUSABLE_OUTCOME候选就会被优先选中）。

**结论：反推数据后，V5.3在MP/MS/RS/ME全部四个组件上都已经达到"能用、和baseline可比"的
门槛，有真实数据支持，不再有"安全但无效"的组件；Step1管线机制已验证，全量训练待启动；
已知缺口都有清楚记录，没有被隐藏或忽略。**
