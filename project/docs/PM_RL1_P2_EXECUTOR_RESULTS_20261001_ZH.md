## 1. 本轮真正推进了什么

在 P1 的明确角色、过去报告、主体及行动阶段表示下，给 114 个 train/dev 前缀各制作六种资源条件的示范。作者只看到该条件真正交付的内容；核验者可以检查这些已获取记忆的原始来源，但其额外资料、审核结论和反馈不会进入学生输入。修复目标也使用原始推理输入训练。

现有本地 Qwen3.5-9B 同时承担示范作者与来源核验，二者有相关错误风险。逐字引用检查只能验证引用绑定，不能证明语义蕴含或主张完整性；另有事前固定的 37 条协调者 AI 原文抽查。它们都不是独立人类真值，也不是 RL 的 q/m 奖励。

补充格式后仍有引用不匹配及 JSON 错误。本轮没有继续搜索提示或把失败记录修成成功。163 条核验未解决包含 71 条来源引用失败、43 条回复引用失败、16 条接纳与检查／主张结论矛盾，以及其他结构问题；它们不等于 163 条回复被证明错误。详细首个失败原因保存在 `review_parse_summary.json`。

**训练后的结构复查发现一个准入实现缺陷。** 723份有效版本核验原文中，7份出现重复JSON字段，4份进入了493条冻结目标（train3、dev1）。P2解析器使用默认的最后值覆盖，导致早先的主张／引文被丢掉；其中一条被丢引文还把原文弯引号改成直引号，原本不应通过逐字检查。因此493是实际程序接纳／使用数，不能再称493条全部通过了严格原始JSON核验；489条未受这次发现的重复键影响，也不等于489条语义金标。

额外逐条读源检查了这4条候选，未发现确证严重的主体／事件捏造；它们仍是事后AI检查，不能补写成事前有效审核。原数据、权重、NLL和选择记录全部保留，不事后删除4条并假称训练用了489条，也没有另开第二次训练。本次执行器作为有这项披露的弱监督开发实验继续比较，后续质量与reward仍必须独立校准。详细记录为 `admission_duplicate_disposition.json`。已有新评分链的 `judge._pairs` 会拒绝重复键，P3须保留该机制；旧P2解析器保持原样以复现实际运行。

## 4. 仍然存在的语义边界问题

本轮把边界转成了可查原文和明确规则，但模型并不总能正确应用：

1. 固定抽查中，一条包含 “the last time we spoke” 的回复仍被模型口头接纳；它因错误引用被程序挡住，不能被当作成功识别身份错误。
2. “密切共事的同事”比原文“合作过的同事”增加了信息，核验者却把整句当成一般支持。这类嵌入在共情或问题中的事实前提仍需检查。
3. 回复使用了过去 MS 中的名字 Max，核验者却标记 ignore；也有 OFF 的当前对话复述被标记 use。因此资源行为字段仅作模型自报记录，OFF 按结构另记 none，不能据此宣布真实资源使用覆盖。
4. 一般共情、澄清问题和礼貌回应不能自动视为事实错误；两个“很高兴能帮到你”的历史归属疑点仅被保守地留为不确定，没有升级成确证严重的 AI 人生经历捏造。

这些发现支持 P3 复用已有 source/reply ID 索引，减少逐字抄引带来的技术缺失，并让有限人工校准检验具体事实前提、严重错误和适当支持的边界。它们不支持直接把 P2 接纳判断改成训练奖励。现有 `judge_explicit.py` v5 仍只是准备版本，没有因为本轮运行而自动取得资格。

## 5. 执行器适配与选模口径

从原始 Llama-3.1-8B-Instruct base 重新开始一次 LoRA：r8、alpha16、q/v、BF16、lr1e-4、microbatch1、累积16、seed17、三 epochs。只对完整回复和 EOT 计损失，不截断训练文本，不继承旧 LoRA 权重。

493 条目标包含 30,591 个 train 目标 tokens、6,166 个 dev 目标 tokens；最长完整序列 2,975 tokens。更新前同一 80 条 dev 目标的 token 加权回复＋EOT NLL 为 1.7865133425。NLL 用于这一弱目标分布上的选模，不能作为支持质量收益。

训练共 78 次优化器更新，更新 3,407,872 个 LoRA 参数；基础模型完整权重哈希在训练前后一致。三轮 dev NLL 分别为 1.279919800、1.153158321、1.117342381。固定 12 个 dev 条件来自 9 个前缀、3 个用户，每轮各生成一次，共 36 条，全部自然结束。未进行第二次训练或效果调参。

协调者 AI 逐条读源核验得到：2 条确证严重错误、7 条不确定、27 条未发现确证严重错误。第一轮两条明确错误分别是把历史支持者的话说成“我说过”，以及把朋友帮助用户转换论文视角的对话说成“我们的对话”。第一轮因此排除；第二、三轮保留，第三轮按较低 NLL 入选。检查并非盲审，协调者知道 epoch 和损失；这些结果不是独立人类评价，也不是新旧执行器质量比较。

| checkpoint | dev NLL | 确证严重错误 | 不确定 | 选模处置 |
|---|---:|---:|---:|---|
| epoch 1 | 1.279920 | 2／12 | 1／12 | 排除 |
| epoch 2 | 1.153158 | 0／12 | 2／12 | 保留 |
| epoch 3 | 1.117342 | 0／12 | 4／12 | 按既定NLL规则选中 |

第三轮并非“不确定最少”，也没有因此被宣布行为最优。未检出确证严重错误与确认无错是不同结论。

这里没有把“不确定”洗成“通过”。例如第二轮将 RS 中“害怕显得软弱”的策略建议说成用户已经提到的感受；第三轮有“别人受优待、却要求你更努力”的未证实补充，还有把历史支持者的概括说成用户提过。它们暴露局部归属／表述问题，但不能仅因存在这些词句就升级成确证严重的人生经历、行动或结果捏造。按既定排除规则保留 checkpoint，同时保留全部疑点交给后续测量检验，不临时改规则以选出某一轮。

第三轮新进程重载通过：整体及80条逐例NLL与保存时完全一致，重载阶段没有参数更新。来源绑定后的执行器身份为 `4666e72612aef698567b2e14fd3315463c451cde64f5cad1299199aaf9e0e811`；完整配置、权重文件哈希及选择记录保存在 `P2/executor_freeze.json`。

## 6. 共同回复池与后续工作

已在查看新执行器输出前冻结 24 个 train 前缀（每用户两个）和全部 18 个 dev 前缀，采用事前同一组 15 个数量向量：630 个名义槽位中 586 个合法、44 个不可行；不可行条件不换成容易条件。固定计划在 dev 不可行时，后续按原方案执行 OFF 并计入总表。

若主执行器选中 LoRA，base 比较另外固定 OFF、一条 RS、一条 MS＋一条 ME，共 54 个名义 dev 槽位，53 个可行、1 个不可行。其对应 LoRA 回复复用主池，不额外挑选有利条件。若主执行器为 base，则无需重复生成相同对照。

共同池 runner 复用既有 `BoundResourceEnv/BoundNaturalGenerator` 来源身份；586 个合法请求已与真实环境的请求逐一核对一致。来源标识仅进入协调者缓存身份，不进入 actor/critic。相同冻结前缀、库存、计划、执行器和 draw 的输出可供后续基线与策略复用。

实际已生成主池586条（train336、dev250）和base对照53条，全部自然结束。42个前缀各有真OFF；53组base／LoRA的模型可见消息、renderer、draw和来源身份全部一致，只有执行器不同。主池输出共47,042 tokens，中位81、最大182；544条非OFF中17条与同前缀OFF文本完全相同，共534个不同的“前缀＋回复文本”。文本不同不证明质量不同，也不证明正确使用了资源；没有将相同文本或缺失评分自动填成奖励0。

另核对行为诊断与主池重合的6个第三轮输入：消息、模型／adapter文件、记录到的运行包及解码配置一致，但只有2组逐token／逐字一致。其余4组从第20、61、65或70个token附近分叉，其中一组改变了是否提出在线支持小组建议，不能都归为标点差异。诊断进程先加载三份adapter再切换，主池只加载选中adapter，这是已知加载差别；根因尚未定位，不能直接断言已证明GPU浮点非确定性。完整补充记录见[跨加载复现限制](pm_rl1_completion_20260930_v2/p2_replay_addendum.json)。因此固定seed／greedy不被宣称可逐字重生回复，有限行为检查也不保证以后没有错误。后续基线与训练复用同一份已保存实际回复；更改加载路径须绑定新身份，不能覆盖原回复。

P2现已收口，P3的完整合法来源准备已完成；接下来组装有明确开发／封存验证用途的有限人工材料，完成新单回复q/m协议的有界校准，达到相应用途后才启动自然任务策略学习。新的人工任务、付费API和RL奖励测量均为0。
