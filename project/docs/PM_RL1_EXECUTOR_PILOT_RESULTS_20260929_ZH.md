## 2. 本批揭示的关键问题

### 2.1 原文存在，不代表它支持抽取的记忆

| profile | 早期有依据的记录 | 后来的错误证据绑定 | 风险 |
|---|---|---|---|
| p18 睡眠困难 | 2024-07-01 自述每天晚上睡眠困难 | 2024-11-05 引文只有 “Hey, are you there?” | 将旧事实伪装成最近重新确认的当前情况 |
| p6 亲密朋友 | 2024-10-05 自述多年好友 | 2024-11-15 引文说与 Lisa 已经结束、仍感到难过 | 继续把已失去的友情当成可用的当前支持关系 |
| p17 宗教团体偏好 | 2024-07-15 自述宗教背景及考虑团体支持 | 2024-07-25 引文只说与朋友关系不顺 | 给旧偏好增加没有依据的新来源和新时点 |

这三项都能通过原有的 ID、角色、原文子串和哈希检查，旧模型 verifier 也接受过它们。但原有 compiler 提示本来就写了“没有当前重新确认，不要重复旧 profile”。因此再加一遍同样的提示不算已经修复。

本批合法历史包含 184 个 session、309 条 MP 和 699 条 ME；同 owner/slot 的相同值再次出现共有 101 次。这是**待核验的重复确认清单**，不是 101 个已证明的错误。三个已确认问题影响本批 4 个选中资源条件；其他条目的语义正确率尚未完成统计，不能报“其余全正确”。

隔离按 owner/slot 而非仅按最新 memory_id 进行，避免删掉“友情仍亲密”的新坏记录后，又自动回退到同样过时的旧记录。原始完整 MS 保留，历史事实不被删除。隔离代码和 manifest 是后续新版本的保护措施，**尚未发布完整修复后的生产资源池**。

### 2.2 好语言仍可能带有关键错误

- 第 8 条 R/17：过去只是讨论过招聘顾问/职业咨询建议，回复却说用户已经求助且减轻了压力，混淆建议与实际行动/结果。
- 第 1 条 L/17：旧事件是朋友因用户重视俱乐部而不满，回复改成了要和“俱乐部里的人”沟通，人物关系发生变化。
- 第 13 条 R：当前是母亲干预交友，回复把早前与父母讨论旅行的一个月带进当前语境；两候选分别拒绝和不确定。
- 第 17 条 L：两候选都采用错误刷新的睡眠 profile，断言最近仍有睡眠问题并转移当前职场诉求；该条件无接受回复。

建议句也会带事实预设，但比喻、普通共情、可选建议不能都按个人事实编造处理。本次每条决定保留具体理由及局限，没有用一条关键词规则代替语义核验。

### 2.3 当前还不足以教会“有效利用历史”

62 条 train 接受候选中，明确带入已核对历史信息的只有 3 个 prefix：1、5、11。许多其他回答与 OFF 相近，或只使用当前已说出的信息。这些回复可以是合适的支持回复，却不足以证明本批提供了充分的资源利用学习信号。

不能为了达到训练门槛，要求作者硬塞记忆，或者给审阅者规定 ON 必须赢。下一版选样需要在**不看输出质量**的前提下，检查可见资源是否有当前输入缺少且确实相关的信息，同时保留资源冗余和应当忽略的情况。

## 3. 为什么这次没有继续 LoRA

生成前合同要求每个 prefix-condition 至少一条接受回复，以及至少 4 个 train prefix 有明确审查过的历史利用。两个门槛都没有达到。程序实际运行到准入检查即退出，没有加载基础模型，也没有伪造 NLL 或 adapter。

这套门槛是本批事前规定的工程/覆盖条件，不是文献证明的普适统计阈值。不能在看到结果后悄悄放宽，再说原计划通过。如果之后采用更合理的覆盖定义，应发布新合同，把本批作为开发发现保留。

**本次准备也有需要纠正的地方。** 前置检查沿用了 `accepted_units`，没有在作者生成前完成所有选中资源的语义及状态审查；条件合同对 16/17 的睡眠 profile 已写“未核实”，但仍放进 L。因此这批 L 中混入了来源错误，不能再解释为纯粹的“合法且真实、仅低相关”的条件。必须承认这一点，不能把事后发现写成完全事前不知。

更不能训练 G 去“识别”只有核验者完整历史才能看出的错误：如果 G 只看到一个错误标成当前事实的 MP，它未必有信息判断该记录已过时。对此优先修复来源/状态表示，或将其作为单独的源错误挑战；不能把核验者的隐藏知识经修复提示回灌作者，也不能把所有后果归因于 G 能力不足。

## 4. 已准备的修复边界与下一批入口

新增 `source_quarantine.py` 包含两层机制：已确认问题按 owner/slot 隔离，未在名单内的条目仍然是“未证明有错”，不自动视为合格；新的生成前检查要求逐资源、逐 prefix 绑定来源审查、合法证据哈希和时态核查，缺失/不确定/哈希变化均拒绝放行。该检查不能自动证明语义正确，下一版生成入口还需按新合同接入。

下一步按以下顺序完成一个有边界的版本更新：

1. 优先检查当前 101 次相同 profile 值再出现的来源，以及新批实际会检索到的 MP/ME；把“旧事实沿用”和“新证据确认”分开，保留原始出处与日期，处理明确的关系结束/状态更新。仅定位的三个问题已隔离，其余不假设自动通过。
2. 不直接修补旧 artifact、旧 BGE 排序或旧缓存。发布来源修复版本，按新资格池重新 materialize/排序，并绑定新 retrieval identity；相同事实的旧 record 不能成为过时 slot 的自动后备。
3. 新批选择同时覆盖可利用历史、无需历史、当前更新覆盖旧历史、应忽略的真实资源。相关性及来源核查在生成前完成；已确认错误的源记忆另列挑战集，不混入常规 L。
4. 再固定作者、逐条准入和覆盖规则，生成后按原定规则收口。通过后才运行已准备的 LoRA、基线/dev NLL、重载和同提示生成诊断。不能宣布本次已经完成这些步骤。

这一轮不新开裁判竞赛，也不把源记忆审计包装成新的人评活动。R04B 的职责、候选范围和最终人评设计见下方独立文件。

## 5. 人评应在什么位置解决什么

推荐保留原定最多 24 对终评：12 对执行器比较、12 对 RL/OneShot 比较，2 名独立人类先单独判断，必要时在同一次组织活动中处理分歧，保留原始意见。当前正式系统未齐，因此没有发新卷，也没有招募/发送消息。

同一批终评可以同时分析系统结果和**已经冻结的自动裁判**的一致性。它不能既用于改 reward/重新训练，又继续宣称为同一版本的独立终评。将人评的一次性目标设为“对冻结版本给出可信结论”，并接受无优势或证据不足，才有可能避免不断重做。

具体试卷、共同合法证据、盲化、equivalent/uncertain、评审身份、旧 A/B 继承范围和 3 个 test owner 的统计限制已写入：[R04B 与一次集中人评方案](PM_RL1_R04B_MEASUREMENT_AND_SINGLE_HUMAN_CAMPAIGN_20260929_ZH.md)。

## 6. 实耗与验证

作者共 47,476 输入、8,642 输出 tokens，108 次全部保留。A6000 的作者加载约 17.55 秒、引擎墙钟约 81.18 秒，完整进程约 115.39 秒；并发为 4，逐请求耗时之和约 288.77 秒不能当墙钟或账单。另有一次 UUID 格式导致的 vLLM 加载前失败，提交请求为 0，改用同一张 A6000 的数字索引后运行；失败记录保留，没有重新生成已完成回复。

BGE 准备整段约 31.37 秒；构造器是惰性的，构造函数的微秒级计时不代表 GPU 权重加载时间。整体准备时间包含实际加载；不要把它漏记成零。

新增付费 API 为 **$0**。核验是本次协调助手逐条审查，不是额外 108 次本地 verifier 调用。训练、重载和 36 次原定诊断生成未发生；没有把未来费用当实耗。开发审阅、环境准备和设备电费没有实测货币计价，因此本地/API 免费不代表研究工时免费。作者的短输出吞吐也不能外推到旧思考型裁判或未来完整训练。

新增准入/隔离与既有编码相关测试共 **27 项通过**，脚本语法检查通过。实际训练入口的提前拒绝已观察；GPU 优化和 adapter 重载尚未实跑，不能以这些测试代替真实训练验证。
