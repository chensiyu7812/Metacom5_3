## 3. 官方 parser 的复刻与一个 upstream 细节

新增 `src/metacom_pm/paper1/evaluation/static_official_scoring.py`，按固定 commit `692624208acc077b8867698c1d6fcd998dee641a` 复刻两个官方 parser，不导入也不执行 upstream 代码：

需要如实记录的一处 upstream 细节：官方 Summary parser 写的是 `except ValueError | json.JSONDecodeError`，这不是合法的 except 表达式，所以 upstream 在内容畸形时抛出的其实是 TypeError 而非返回空判定。我们保持相同的输入—输出行为（解析不了就没有分数），但把每次失败显式记录下来，而不是复刻那次崩溃。

## 7. 付费评分路径的离线端到端验证

把 80 脚本里的付费循环抽成可注入传输的 `execute_payloads(...)`，用假的 `send` 走通全路径，不花钱也不接供应商。13 项新测试覆盖：

- 成功调用按**实测用量**结算，而不是按预留上限；
- 每次尝试在发送前都已按「完整输入 + 16,384 原生输出」写入预留；
- 供应商错误重试恰好一次后停止，且**不继续烧下一条**；
- 传输失败按预留上限保守计账（两次尝试都记满额）；
- 一次瞬时失败后重试成功；
- 官方回复解析不了 → 记 `OFFICIAL_PARSE_FAILED`、无分数、**不是零分**，且不算传输失败；
- Summary 回复产出 Event F1 作为主指标；
- 阶段额度与累计额度**在会突破的那条预留之前**停下；
- 断点恢复只跑剩余条目，不重发任何请求；
- `project_retry_max=0` 时不重试；
- 落盘记录带齐恢复所需的完整身份。

### 测试暴露并修掉的两个真实缺陷

1. **结果文件丢失会导致重复计费。** 原实现按磁盘上的分数文件决定待办；若某条已成功付费但结果文件丢失，恢复时会撞上「reservation ID 已存在」而中断，或在别的路径下重复发送。现在 `execute_payloads` 先查账本 `has_successful_call_hash(...)`，已成功结算的调用直接跳过并记入 `skipped`。为此在 `api_budget.py` 增加了一个只读方法 `has_successful_call_hash`（该文件因此成为 tracked-modified）。
2. **累计额度的停止判据用错了线。** 原来只和 `$50 − 已计` 比，但账本对非重试调用实际执行的是「必须保留 $5 主运行重试额度」即 `$45` 线。结果是预留会在运行中途抛异常，而不是干净地停下。现在按 `$45` 线预检并干净停止，`stopped` 里带上 `primary_ceiling_usd`。

第三个测试失败是我自己的假设写错了：阶段额度按**已结算实际值**累加，而单条预留按**最坏值**检查，所以 $0.30 的上限并不会在第二条就停。已把测试改成用「恰好一条预留」的上限来验证真正的语义。

## 10. 78 绑定：1,924 全部绑定，0 排除

并且暴露了一个**只有真实数据才会出现的情况**：`80` 原先对重复 `call_hash` 直接报错退出。

原因是真实的：不同 k 有时让 Generator 产生**逐字相同**的回答，于是官方评分 payload 也逐字相同。全量统计：**1,924 条中 293 条（15.2%）与另一条完全相同，去重后只剩 1,631 条**。

**需如实披露的代价**：官方 scorer 省略 temperature，同一 prompt 再调一次本可能得到不同分数；复用消除了这部分「重复内方差」。这是有意的偏离，不是等价替换。
